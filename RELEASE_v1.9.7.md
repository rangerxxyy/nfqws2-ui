# v1.9.7 — Быстрая загрузка списка версий

## Изменения

- Списки версий nfqws2-UI и nfqws2 ограничены десятью последними релизами вместо тридцати и ста.
- Backend сохраняет каталоги релизов обоих проектов на роутере на 12 часов; повторное открытие окна использует кэш. Кнопка «Обновить» в окне UI и nfqws2 принудительно запрашивает свежий список; автоматические повторы после сетевой ошибки ждут 10 минут. При недоступности GitHub показывается сохранённый список с предупреждением. Это сокращает число обращений к GitHub по сравнению с Xkeen UI, который запрашивает список из 10 релизов при каждом открытии.
- Отдельная проверка статуса обновления UI и кэширование статуса nfqws2 сохраняют прежнее поведение.
- Метрики RAM и CPU из локального Keenetic RCI обновляются не чаще одного раза в 5 секунд вместо каждого трёхсекундного опроса UI. Недоступный RCI тоже кратковременно кэшируется, а значения из `/proc` остаются fallback.
- Команда `S99nfqws2-ui status` проверяет реальный TCP LISTEN для выбранного backend-порта, поэтому больше не считает зависший HTTP-сервер исправным только по PID.
- Возвращён раздел «Отчёт для помощи» с ручным созданием, копированием и скачиванием диагностической сводки. Маскирование сайтов включено по умолчанию; содержимое конфигурации, списков и секреты не добавляются, отправка не выполняется автоматически.
- Добавлен раздел «Файлы после обновлений» по поведению Zemidala: в каталоге конфигурации и `lists/` ищутся все прямые файлы с суффиксами `-opkg`/`.apk-new`; показываются размер, дата и совпадение с исходником. Для изменённых `nfqws2.conf` и `.list` появилась кнопка «Сравнить»; содержимое запрашивается только по нажатию и показывается рядом с исходником. Удаление требует подтверждения и сервер повторно проверяет кандидатов; активные файлы не передаются и не меняются.
- Инвентаризация списков показывает, какие профили используют файл и с какой ролью. Удаление подключённого пользовательского списка блокируется как в Zemidala; при невозможности разобрать конфигурацию UI не заявляет, что список свободен.
- Быстрый выбор `ISP_INTERFACE` ставит текущие интерфейсы из конфигурации и интерфейсы default route выше остальных. Default route читается локально из `/proc/net/route` и `/proc/net/ipv6_route`; ручной ввод поддерживает до 16 безопасных имён через пробел, как Zemidala.
- Стратегии сообщества старше 60 дней остаются в подборе после свежих вариантов и получают пометку «давно не подтверждалась», как в Zemidala; совпадения точного сайта и ASN-сети ранжируются выше общих. ASN хоста кэшируется на сутки; lookup использует сначала DNS роутера, затем публичный DoH, ограничен по времени и пропускается, когда в базе нет ASN-целей.
- Перед завершением применения конфигурации проверяются до 20 сайтов с недавним успешным результатом в «Мониторинге». Если доступность не подтверждается повторной проверкой, UI автоматически возвращает предыдущую конфигурацию и перезапускает службу.
- Результаты проверки «Обрыв на 16 КБ» сравниваются с текущими профилями и порядком маршрутизации. Сверяются списки-файлы, inline-условия `--ipset-ip`, `--hostlist-domains`, `--ipset-exclude-ip`, `--hostlist-exclude-domains` и `--hostlist-auto`; поддерживаются IPv4/IPv6 диапазоны. UI показывает профиль, принимающий адрес, объясняет известные исключения и скрывает повторное применение только при подтверждённом совпадении на текущем маршруте. Недоступные списки и неподдерживаемые условия оставляют маршрут непроверенным. Статус добавляется только в ответ API и не меняет сохранённые результаты.

## Проверки

- Полный backend test suite и тест ограничения GitHub API до 10 релизов.
- Rust-тест срока и содержимого кэша метрик RCI.
- Полный frontend test suite, TypeScript typecheck и production build.
- Rust fmt и Clippy; release workflow дополнительно проверит shell-скрипты, зависимости и ARM64 Linux musl пакет.
- Shell preflight проверяет вывод статуса при отсутствующем слушателе, рабочем порте и отсутствующем port file.
- Backend-тесты сканирования и API проверяют ограниченную выдачу сравнения, допустимые исходники, защиту от traversal и сохранность активной конфигурации/списков.
- Backend-тесты list inventory и delete API проверяют роли профилей и отказ удаления используемого списка.
- Backend-тест выбора сайтов для проверки ограничивает набор свежими успешными результатами; транзакционные тесты проверяют откат конфигурации при провале post-restart проверки.
- Backend-тесты проверки обрыва подтверждают порядок профилей, нормализацию `strategy=N`, безопасное поведение при исключениях/недоступных списках и то, что маршрутные сведения не сохраняются в операцию сканирования.
- Frontend-тесты проверяют сообщения о текущем/другом/неопределённом профиле и скрытие повторного применения только при подтверждённом совпадении.
