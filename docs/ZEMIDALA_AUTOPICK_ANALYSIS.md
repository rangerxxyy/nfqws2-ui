## zapret2 sources

Pinned `zapret2` is MIT licensed (`LICENSE`). `blockcheck2.sh` is the real modular test runner; it picks a PID-derived NFQUEUE (`$$ % 64536 + 1000`), PID-specific mangle chain names, installs scoped rules, and has traps/cleanup and stale-resource cleanup. `blockcheck2.d/standard/def.inc` defines supported foolings such as `tcp_md5`, `badsum`, sequence/ACK/timestamp/flags, `ip_ttl` and `ip_autottl`; modules `10-http-basic.sh`, `20-multi.sh`, `25-fake.sh`, and `35-hostfake.sh` test HTTP rewriting, TLS split/disorder, fake packets and hostfakesplit. Exact available options still depend on the installed version/Lua scripts; candidates must be checked against the target binary before launch. `docs/manual.md` describes blockcheck2’s HTTP/TLS/HTTP3 tests and treats repeated volume stall as evidence, not proof. No PHP runtime should be added.

The source tree includes additional `blockcheck2.d` test modules; not every module is safe or relevant for a web-driven router-side job. `blockcheck2.sh` chooses PID-derived QNUM and process-specific iptables/nftables names near the top, scopes firewall setup by platform, and uses `sigint_cleanup()`/`sigsilent()` around lines 2030–2062 plus normal `cleanup` near line 2078. `unprepare_all()` also kills and waits for test children and removes owned packet-filter rules. Any later port must keep per-test time/resource limits and clean only process-owned rules. No shell fragment from the script was transplanted.

## Recheck of the upstream picker flow — 2026-10-23

The live GitHub `main` version of `src/www/api.php` was re-opened after the initial pinned audit. The candidate sources and order are explicit in `testJob()` (around lines 4460–4535 in the currently fetched source):

1. `configCandidates()` extracts strategies from active profiles matching the selected protocol/port/payload.
2. `STD_HTTP`, `STD_TLS` or `STD_QUIC` contributes the small standard set when selected.
3. A strategy pasted from an existing profile is prepended; strategies entered in the custom form are prepended after exact-step deduplication.
4. `catalogCandidates('ext'|'full', …)` generates the blockcheck2-style catalog. Upstream comments describe roughly 330 extended TLS candidates and roughly 3,000 full candidates; every candidate is checked against the installed Lua function catalog before execution.
5. `picksCandidates()` adds prior successes, preferring the same host and protocol, then optionally a small number of other-host successes.
6. `communityCandidates()` downloads provider-ASN-specific entries from `zemidala/nfqws2-strategies`; these remain untrusted candidates and are locally validated and probed.
7. For HTTPS, `freezeCandidates()` may add fake-SNI variants discovered by the 16 KB network scan.

The selected list is a source of candidates, not an outcome: `testJob()` probes using the real network request and test nfqws2 instance. Baseline DNS/TCP checks short-circuit when a strategy cannot help. In the ordinary sequential path, each candidate must meet the requested repeat count. In automatic mode (`auto`), the first candidate meeting all repeats ends the search. For large catalogs, `parSlots()` chooses bounded parallel batches; successes from a batch are then checked serially because upstream documents false positives from simultaneous connections to the same site. `testRefine()` optionally varies fake parameters when results warrant it.

The current Rust implementation now additionally supports one custom candidate with strict `--lua-desync` grammar/Lua/blob validation, configurable 2–5 real confirmations (default 3), reuse of previously confirmed candidates, generated extended and full HTTP/TLS catalogs, candidates confirmed by the latest 16 KB scan, optional community candidates for the router's provider ASN, and optional stop-after-first-confirmed mode. History/catalog candidates are still probed afresh. The full blockcheck2 generator now ports the upstream `CAT_FOOL`, split positions, `fakes()`, hostfakesplit modes, fake+split combinations, fakedsplit/fakeddisorder, `tcpseg` and repeats axes; it filters every candidate through the installed Lua/blob catalog and caps plans at 4,096 entries. Its fake-parameter refinement now varies the upstream axes one at a time, with live checks and a five-minute ceiling.

At the time of the initial audit, full-catalog lane helpers were not yet wired into the runner. The current implementation calls `run_full_candidates_with_batches()` from `backend/src/main.rs`, uses `site_trace::run_candidate_batch()` for isolated lanes, and caps each batch at `probe_lanes::MAX_BATCH_LANES` (3). Batch positives are rechecked serially; allocation/setup uncertainty falls back to sequential probing, and operation state is bounded. This remains deliberately smaller than upstream's 15 lanes. Unit tests cover lane selection, fallback, cancellation and rechecks; real router batch execution is still unverified.

On 2026-10-23 a read-only SSH check of the authorized router confirmed the nfqws2 process uses queue 300 and observed approximately 497,680 kB total and 203,872 kB available memory. No NFQUEUE test process, firewall change, config change or service restart was performed during that check. Router-side behavior of the new picker remains unverified.

## Recheck of current upstream and router state — 2026-10-24

The current local upstream checkout is `3ec0fdf6281abe6762b02fb2937173462cc56f81`. Re-read `src/www/api.php` at that revision rather than assuming the older audit still matches:

- `volumeFrozen()` uses a randomized 64 KiB HTTPS POST (`VOLUME_BYTES`, 8 second total timeout) and classifies a timeout after `CURLINFO_APPCONNECT_TIME > 0` as a possible upload stall. This does not measure an exact 16–20 KiB receive boundary and does not prove DPI.
- `curlProbe()` first requests a bounded 64 KiB response range; if the HTTP response is smaller than 24 KiB it runs the POST fallback. The timeout reason maps to the freeze label only when an HTTP status was received.
- `padProbe()` (`PAD_REQS=12`, `PAD_BYTES=4000`) makes a sequence of padded HEAD requests on one curl connection using `--fail-early`; a server that reconnects or does not hold the connection is classified as untestable rather than frozen.
- `freezeJob()` first probes references without the test strategy. A timeout before HTTP response is also treated as a stall only when an independent TCP probe succeeds. Each fake-name candidate gets three successful isolated route probes to be accepted; after the first failed probe it waits three seconds and retries. A name discovered on another reference in the same verified ASN is reused, with that provenance recorded.
- `parSlots()` / `parTry()` use up to 15 mark/port lanes, recursively split a batch if nfqws2 rejects its configuration, and individually re-test batch positives (up to 24 confirmations, stopping after 8 confirmed results). The source uses a 64-port range per lane and marks in `0x0f000000`; those constants describe upstream's environment and are not safe to assume on another router.

The live router was inspected read-only via SSH on port 222. Queue 300 still belongs to the primary nfqws2. At this later inspection, queues 301 and 302 were already occupied by other test processes, so no additional probe was started. `MemAvailable` was 204,692 kB, total RAM 497,680 kB, and load average 0.31 / 0.30 / 0.19. Existing policy rules include fwmarks for xkeen and there are other active test rules; candidate lane marks must be derived from current state and queue availability checked immediately before a real run.

In the current Rust branch, deterministic lane allocation, bounded resource sizing (three lanes maximum), per-candidate multi-profile argv generation, and target/local-flow-scoped mark-rule generation have been added with unit coverage. These helpers are not yet wired into a live batched router runner. The full picker remains sequential until the runner, batch-positive serial confirmation, cleanup/fallback behavior and router safety checks are integrated; this branch is not ready to release.
## Follow-up: timeout classification, ASN and one-click application (2026-10-24)

- Zemidala's `freezeJob()` treats a baseline timeout as a possible stall only when an independent TCP connection to that address/port succeeds. It then probes fake-SNI candidates and reports a found strategy only after three successful checks. Rust now applies that same gate: a direct timeout (before response, before body, or after body) triggers a TCP-only control probe; reachable TCP changes the result to *possible* freeze and permits candidate search. This still does not establish DPI or a byte-exact 16 KB cutoff. A timeout with failed/unavailable TCP remains inconclusive.
- RIPEstat `network-info` returns `data.asns` as strings, e.g. `["396982"]`. The former Rust parser accepted only JSON integers, which explains the UI's persistent “ASN не подтверждён”. The parser now accepts positive integer strings as well as numeric JSON values, rejects malformed/zero values, and still compares live data to pinned catalog hints.
- The explicit per-domain “Применить к сайту” action now performs the server-side preview and apply workflow in one click. The backend revalidates that the candidate came from this domain and passed three checks, checks config revision and `nfqws2 --dry-run`, then backs up, restarts and rolls back on failure. A pending unsaved editor draft blocks this action. This is guarded single-domain application, not unattended automatic application.

## Current implementation update — 2026-10-24

- The backend/UI requested behavior is intentionally worded more cautiously than the upstream: a transfer timeout itself is shown red as «Возможный обрыв» and triggers fake-SNI candidate checks after the baseline pass, but it is not described as proof of a 16–20 KB stall or DPI. Explicit DNS/connect/TLS failures do not trigger candidate search.
- Full HTTP/TLS catalog probing now has a bounded three-lane implementation. It derives lane marks around currently reserved firewall and policy bits, uses isolated source-port ranges and an unused NFQUEUE, and serially confirms batch positives by measured latency. Any resource or setup uncertainty falls back to serial. This is not a claim of identical concurrency to upstream's 15 lanes; router memory is lower and lane allocation is recalculated per batch.
- The 16 KB screen now displays the current numbered network step, a progress bar, and active substeps; the fake-SNI phase states the three-success rule. Confirmed strategies on user-entered domains expose one-click apply with the existing transactional safeguards.
- Release `v0.4.0` was published from merge commit `ce39a3a7acb01284492770ec6e9e6615168a50d5`; its CI and release workflows passed. The full catalog and bounded batch runner are integrated, including resource-aware lanes, source-port/fwmark separation, queue discovery, positive rechecks through the isolated serial path, fallback and cancellation cleanup. Device-side batch strategy execution remains unverified; no claim of live router equivalence is made.

## Recheck of third-party `.conf` checks — 2026-10-25

- Zemidala's `cfgPrepare()` runs `cfgUnsafe()` before any shell parsing; only assignment/comment lines are accepted and command substitutions/backticks are rejected. It then calls `adaptConf()` to map known paths from Keenetic/Entware, OpenWrt, zapret v1 and zapret2 onto the installed layout, adds missing standard variables/Lua init modules, runs full config lint/dry-run, and extracts profiles for isolated tests. During probes it redirects `--hostlist-auto` to a temporary copy so a test cannot modify the user's auto-list.
- `cfgJob()` checks the active config first, tests each candidate serially against the same sites, performs up to three requests per site and stops repeats on first failure. It records per-site results and resource-gates full-config test processes. The current Rust UI deliberately does not source/evaluate a full shell config or apply it; it parses supported argument assignments and starts the existing isolated runner. Limits remain three candidate configs and three sites to bound router work.
- The Rust foreign-config checker now maps Lua and blob file references by known name to the active installation's exact paths, while still rejecting any Lua module not already active. Each candidate/site gets up to three sequential confirmations, stopping after an unsuccessful or inconclusive probe; the UI states the retry rule and shows the successful-attempt count. The checker keeps its existing HTTPS-only public IPv4 pin, no-redirect policy and 64 KiB per-config cap, rather than adopting upstream's broader URL behavior.
- GitHub `owner/repo/blob/ref/file` links are converted to `raw.githubusercontent.com` before fetch, matching Zemidala's convenience while keeping the Rust fetch pinned to a public address with no redirects.
- Remaining deliberate difference: this checker does not rewrite every distro-specific list/log/interface path or inject missing config variables, and it does not use/apply the adapted full config. An unknown path therefore fails the isolated dry-run or candidate launch visibly rather than being guessed. `--hostlist-auto` mutation is not enabled for foreign configs. A dedicated test copy may be considered if future config support needs those semantics.
