## zapret2 sources

Pinned `zapret2` is MIT licensed (`LICENSE`). `blockcheck2.sh` is the real modular test runner; it picks a PID-derived NFQUEUE (`$$ % 64536 + 1000`), PID-specific mangle chain names, installs scoped rules, and has traps/cleanup and stale-resource cleanup. `blockcheck2.d/standard/def.inc` defines supported foolings such as `tcp_md5`, `badsum`, sequence/ACK/timestamp/flags, `ip_ttl` and `ip_autottl`; modules `10-http-basic.sh`, `20-multi.sh`, `25-fake.sh`, and `35-hostfake.sh` test HTTP rewriting, TLS split/disorder, fake packets and hostfakesplit. Exact available options still depend on the installed version/Lua scripts; candidates must be checked against the target binary before launch. `docs/manual.md` describes blockcheck2’s HTTP/TLS/HTTP3 tests and treats repeated volume stall as evidence, not proof. No PHP runtime should be added.

The source tree includes additional `blockcheck2.d` test modules; not every module is safe or relevant for a web-driven router-side job. `blockcheck2.sh` chooses PID-derived QNUM and process-specific iptables/nftables names near the top, scopes firewall setup by platform, and uses `sigint_cleanup()`/`sigsilent()` around lines 2030–2062 plus normal `cleanup` near line 2078. `unprepare_all()` also kills and waits for test children and removes owned packet-filter rules. Any later port must keep per-test time/resource limits and clean only process-owned rules. No shell fragment from the script was transplanted.

## Existing nfqws2-ui mapping

- `backend/src/site_trace.rs`: existing `select_trace_queue`, `trace_argv`, local target validation, scoped rule generation, trace lifecycle. Queue selection consults process argv, firewall snapshot and `/proc/net/netfilter/nfnetlink_queue`; scoped rules use unique chains and remove only inserted rule specs. This is the preferred starting point for the test environment manager.
- `backend/src/site_diagnostics.rs`: existing public-domain normalization, DNS/TCP/route checks, bounded curl capture, current-route and bypass probes, HTTP/3 advertisement and typed report. `capture()` caps response bytes and kills subprocesses on drop/timeout, but the current public diagnostic does not classify byte-boundary stalls.
- `backend/src/main.rs`: Axum site endpoints and persistent trace operations, including cancellation controls and bounded operation storage. New strategy/transfer tasks should follow this pattern while sharing a conflict guard.
- `web/src/api.ts`, `web/src/panel.ts`, `web/src/App.tsx`: typed diagnostics endpoints, tab wiring and trace UI; preserve these patterns and existing visual system.

## Recheck of the upstream picker flow — 2026-10-23

The live GitHub `main` version of `src/www/api.php` was re-opened after the initial pinned audit. The candidate sources and order are explicit in `testJob()` (around lines 4460–4535 in the currently fetched source):

1. `configCandidates()` extracts strategies from active profiles matching the selected protocol/port/payload.
2. `STD_HTTP`, `STD_TLS` or `STD_QUIC` contributes the small standard set when selected.
3. A strategy pasted from an existing profile is prepended; strategies entered in the custom form are prepended after exact-step deduplication.
4. `catalogCandidates('ext'|'full', …)` generates the blockcheck2-style catalog. Upstream comments describe roughly 330 extended TLS candidates and roughly 3,000 full candidates; every candidate is checked against the installed Lua function catalog before execution.
5. `picksCandidates()` adds prior successes, preferring the same host and protocol, then optionally a small number of other-host successes.
6. `communityCandidates()` downloads provider-ASN-specific entries from `zemidala/nfqws2-strategies`; these remain untrusted candidates and are locally validated and probed.
7. For HTTPS, `freezeCandidates()` may add fake-SNI variants discovered by the 16 KB network scan.

The selected list is a source of candidates, not an outcome: `testJob()` probes using the real network request and test nfqws2 instance. Baseline DNS/TCP checks short-circuit when a strategy cannot help. In the ordinary sequential path, each candidate must meet the requested repeat count. In automatic mode (`auto`), the first candidate meeting all repeats ends the search. For large catalogs, `parSlots()` chooses bounded parallel batches; successes from a batch are then checked serially because upstream documents false positives from simultaneous connections to the same site. `testRefine()` optionally varies fake parameters when results warrant it.

The current Rust implementation now additionally supports one custom candidate with strict `--lua-desync` grammar/Lua/blob validation, configurable 2–5 real confirmations (default 3), reuse of previously confirmed candidates, generated extended and full HTTP/TLS catalogs, candidates confirmed by the latest 16 KB scan, optional community candidates for the router's provider ASN, and optional stop-after-first-confirmed mode. History/catalog candidates are still probed afresh. The full blockcheck2 generator now ports the upstream `CAT_FOOL`, split positions, `fakes()`, hostfakesplit modes, fake+split combinations, fakedsplit/fakeddisorder, `tcpseg` and repeats axes; it filters every candidate through the installed Lua/blob catalog and caps plans at 4,096 entries. Its fake-parameter refinement now varies the upstream axes one at a time, with live checks and a five-minute ceiling.

The full plan is currently tested sequentially. Upstream's `parTry()` instead uses one nfqws2 process with per-candidate `--filter-mark` lanes and corresponding source-port ranges, then individually confirms candidates that passed in a batch. Rust now reuses a single isolated process and queue/rules for the sequential confirmations of each candidate, but does not yet route concurrent flows to distinct strategy lanes. Running several instances concurrently would risk overlapping test traffic, so concurrency remains disabled until that lane routing and device resource behavior are implemented and tested. Full-mode negative candidates are aggregated and the stored result list is capped at 256 to keep operation files bounded; successful and partial outcomes remain available. This is a real full candidate catalog with fewer per-repeat restarts, but not timing/parallelism equivalent to upstream.

On 2026-10-23 a read-only SSH check of the authorized router confirmed the nfqws2 process uses queue 300 and observed approximately 497,680 kB total and 203,872 kB available memory. No NFQUEUE test process, firewall change, config change or service restart was performed during that check. Router-side behavior of the new picker remains unverified.
