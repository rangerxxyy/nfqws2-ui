# Трассировка сайта через nfqws2 — спецификация

## Цель

Добавить в раздел «Проверка сайта» трассировку, запускаемую с компьютера пользователя, но выполняемую Rust backend на роутере. Для введённого публичного домена панель отдельно показывает, отвечает ли сайт без обработки nfqws2 и с активными стратегиями nfqws2, а также показывает ограниченный журнал тестового процесса.

## Пользовательский поток

1. Пользователь вводит домен в существующее поле диагностики и запускает «Трассировку».
2. Панель показывает этапы «Без nfqws2» и «С nfqws2», время и HTTP-статус/понятную причину результата.
3. Для этапа «С nfqws2» панель показывает журнал тестового экземпляра, разбитый на строки, с прокруткой и отметками ошибок. Длинный журнал ограничен backend и имеет явный признак усечения.
4. По завершении панель формирует итог: открывается ли сайт без nfqws2, открывается ли с nfqws2, либо результат неопределён из-за локальной ошибки/отсутствующей возможности.

Результат является проверкой сетевого пути самого роутера. Он не утверждает, что клиентское устройство использует тот же маршрут.

## Архитектура

- UI остаётся TypeScript/TSX и оформляет отдельный пункт «Трассировка» рядом с существующим «Проверка сайта» в текущей навигации и визуальном стиле.
- Раздел «Проверка сайта» сохраняет текущую быструю диагностику. Раздел «Трассировка» имеет отдельный экран с доменом, запуском, статусом и подробным журналом; запуск одного раздела не меняет состояние другого.
- `web/src/api.ts` получает типизированный метод `diagnostics.trace(host)`.
- Rust добавляет отдельный маршрут `POST /api/nfqws2/diagnostics/trace` и сериализованные типы отчёта.
- Обе проверки выполняются последовательно под общим lock диагностики, чтобы не пересекаться с другими пробами.
- Для baseline используется HTTPS-запрос с тестового source-port диапазона, который исключается из штатной обработки nfqws2 временными узкими правилами.
- Для результата «с nfqws2» Rust запускает отдельный экземпляр найденного `nfqws2` на временной NFQUEUE. Его аргументы основаны на проверенном снимке активного argv штатного процесса; конфликтующие аргументы процесса (`qnum`, daemon/pidfile/debug/user) фильтруются и задаются backend явно. Главный процесс nfqws2 не останавливается и не перезапускается.
- Временные правила создаются в выделенных цепочках с уникальным идентификатором операции. Совпадение ограничивается локальными соединениями роутера к выбранному публичному IPv4:443 и выделенному source-port диапазону. Правила удаляются в общем cleanup-пути до возврата ответа.
- До добавления даже временного перехода из системных hooks backend проверяет существующие правила и фактический init-скрипт. Если штатный скрипт владеет теми же hooks/цепочками или безопасное сосуществование нельзя доказать, операция завершается без изменения firewall. Существующие цепочки/правила init-скрипта не редактируются и не очищаются.
- Запуск процессов выполняется через Rust `Command` с фиксированным executable и отдельными аргументами; команды iptables и curl не собираются в shell-строки. Дочерние процессы принадлежат операции и завершаются по timeout/error.

## Сетевая проверка и безопасность

- Повторно используется нормализация домена и проверка публичности IP из `site_diagnostics`.
- Локальные, зарезервированные и не публичные назначения отклоняются до изменения правил.
- Выбирается один разрешённый публичный IPv4-адрес, ответивший при DNS-резолвинге. В отчёте указывается фактический адрес.
- Ни конфиг, ни списки, ни файлы сервиса не изменяются. Основной nfqws2 остаётся запущен.
- Очередь выбирается динамически из ограниченного диапазона и проверяется на конфликт с активной конфигурацией/процессами; при невозможности надёжно выделить очередь операция завершается без установки правил.
- Каждый iptables шаг проверяется. Если цепочку/правило невозможно установить, обработчик удаляет уже созданные элементы и возвращает диагностическую ошибку.
- Cleanup удаляет только точные уникальные правила и цепочки текущей операции; он не использует flush/delete общего системного chain и не вызывает stop/restart init-скрипта.
- Таймаут охватывает оба HTTPS-запроса, старт тестового процесса и чтение журнала. Cleanup должен выполниться до возврата из обработчика даже при ошибке запуска или таймауте.
- Лимиты фиксированы: один домен, один IPv4, один запрос на каждый режим, конечный timeout, ограниченный размер журнала и ограниченное число строк в JSON.
- `HTTP 4xx/5xx` считается полученным ответом сайта; отдельный код/статус отображается, но не приравнивается к сетевой недоступности.

## Поведение при ошибках

- DNS не дал публичный IPv4: тест не изменяет firewall и возвращает понятную ошибку.
- Нет curl, iptables, активного nfqws2, читаемого снимка argv или возможности открыть отдельную очередь: baseline выполняется, если это безопасно; этап с nfqws2 отмечается «не выполнен» с причиной.
- При ошибке baseline этап «с nfqws2» всё равно выполняется, если предварительные проверки позволяют безопасно создать изолированный процесс.
- При ошибке создания правил обработчик очищает только цепочки своей операции; чужие цепочки и правила не меняются.
- Timeout/отмена/ошибка процесса не показываются как «сайт заблокирован»: это отдельный технический статус.
- Журнал является диагностическими данными, не HTML; UI выводит его текстом и не интерпретирует разметку.

## Тестирование

- Rust unit tests: доменная валидация, выбор/отказ очереди, генерация argv/rule vectors, состояния cleanup при частичном создании правил, интерпретация HTTP- и process-результатов, усечение журнала.
- Rust router tests: endpoint отклоняет локальные и инъекционные host до запуска процессов; сериализация включает оба результата; конкурентный запуск получает conflict.
- Frontend tests: вызов типизированного API, промежуточное состояние, оба независимых результата, ошибки/неопределённый статус, безопасное отображение журнала и усечение.
- UI navigation test: «Проверка сайта» и «Трассировка» существуют как два самостоятельных раздела и переключаются независимо.
- Локальные тесты не устанавливают firewall-правила и не требуют nfqws2. Роутерный smoke test запускается только отдельно на устройстве с явной проверкой интерфейса/активного бинарника; отсутствие Keenetic/роутера в среде разработки не маскируется под успешный hardware test.

## Вне области

- Классический traceroute с TTL и списком промежуточных маршрутизаторов.
- QUIC/HTTP3 диагностика и перебор стратегий.
- Изменение текущей конфигурации, остановка штатного сервиса, применение найденной стратегии.
- Удалённое тестирование клиентских устройств.

## Самопроверка спецификации

- Обе стороны сравнения имеют отдельные итоговые статусы; технические ошибки не называются блокировкой.
- Проверка основана на реальном active argv, а не на придуманных или захардкоженных стратегиях.
- Условия безопасности и cleanup покрывают частичное создание firewall-правил и отказ старта дочернего процесса.
- Проверка ограничений приложенного задания не допускает редактирования firewall-правил, принадлежащих init-скрипту; при неоднозначном владельце действует fail-closed.
- В запросе есть только домен; пользователь не передаёт произвольные аргументы, пути, интерфейс или команды.
- Локальные тесты не трогают сетевые правила; аппаратный smoke test остаётся отдельным и честно не подтверждается без роутера.
