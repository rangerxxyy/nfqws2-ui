# Применение проверенной стратегии nfqws2

## Intent

После успешного автоподбора пользователь должен иметь возможность увидеть точный план изменения и применить его с резервной копией, проверкой работы службы и автоматическим откатом, если сайт не открылся. Это продолжает workflow Zemidala `autoApplyList` / `autoApply`, но использует существующие Rust API и интерфейс nfqws2-ui.

## Current state

`StrategyPickOperation` сохраняет домен и кандидатов, а кандидат помечается `confirmed` только после двух успешных изолированных сетевых проб. Конфигурационный API уже умеет проверять revision, сохранять резервную копию, перезапускать службу и откатывать конфиг при ошибке рестарта. Связующего endpoint между подтверждённым результатом и этим API пока нет. `NFQWS_ARGS_CUSTOM` — единственная переменная, где package init допускает добавление `--new` профиля. Upstream сначала добавляет домен в hostlist только если доказано, что совпавший активный профиль уже подходит; иначе добавляет отдельный профиль для домена, выполняет dry-run, перезапускает службу и перепроверяет домен.

## Approaches

1. **Показывать копируемые параметры без применения.** Минимальный риск, но не выполняет запрос на безопасное применение и автоматический откат.
2. **Отдельный backend apply workflow поверх текущего config transaction.** Рекомендуемый путь: preview получает только persisted подтверждённый результат, генерирует безопасное изменение в `NFQWS_ARGS_CUSTOM`; apply требует ожидаемую revision и повторно проверяет сохранённую задачу, запускает `nfqws2 --dry-run`, пишет резервную копию, перезапускает службу, делает bounded повторные запросы к целевому домену и откатывает файл/службу при неудаче. Если соответствие текущему профилю и его существующему hostlist не подтверждено однозначно, применяется отдельный профиль только для домена.
3. **Изменять конфиг и список раздельными вызовами из браузера.** Неатомарно при потере соединения и не позволяет backend гарантировать откат; не выбирается.

## Goals and constraints

- Переиспользовать существующие lock, revision, backup, config validation, service restart и rollback primitives.
- Принимать только ID завершённой операции и индекс кандидата; стратегию и аргументы брать из сохранённого `confirmed` результата, никогда из произвольной shell-строки браузера.
- Не допускать QUIC и неподтверждённые кандидаты; блокировать конфликтующие диагностики и config writes.
- Сохранять пользовательские строки, comments и неизвестные опции; неоднозначный/динамический `NFQWS_ARGS_CUSTOM` отклонять с инструкцией исправить raw-конфиг вручную.
- В preview показывать target, выбранный вариант, точный diff и revision; запись выполняется только отдельным действием пользователя.
- Проверять конфигурацию установленным бинарником через `--dry-run` до рестарта. После изменения проверять состояние службы и делать ограниченные сетевые повторы для target. При неуспехе восстанавливать исходный контент с compare-and-swap защитой и повторным рестартом.
- Текущие ограничения: локальная машина не имеет подключённого Keenetic; системные команды и end-to-end firewall/network поведение остаются target-only проверками.

## Acceptance

- Нельзя получить preview/apply для неподтверждённого, отменённого, чужого или QUIC-кандидата.
- Повторная/устаревшая revision блокируется без side effects.
- Dry-run failure не меняет конфиг и не перезапускает службу.
- Сбой рестарта или целевого сайта возвращает исходный конфиг, если никто не менял его после применения; успешный apply оставляет backup.
- Пользователь видит diff и подтверждает изменение отдельно от подбора.
- Unit/API tests проверяют реальные файлы в tempdir и callback последовательность; hardware-only проверки явно отмечены.
